# Engine plan

GGUF-Header (milestones 1 to 8 in `ROADMAP.md`) gives the engine a compile-time
description of the model. This plan covers what comes after it: a single persistent CUDA
kernel that runs one decode step, scheduled at compile time and checked against llama.cpp.

## Target

- **Decode only, batch size 1.** No prefill kernel yet: prompt tokens go through the
  decode path one at a time.
- **Qwen3-0.6B, BF16** (`models/Qwen_Qwen3-0.6B-bf16.gguf`).
  - 28 layers, hidden 1024, FFN 3072
  - 16 query heads and 8 KV heads, head_dim 128 (from `attention.key_length`; it is
    **not** 1024/16)
  - RoPE base 1e6, RMSNorm eps 1e-6, vocabulary 151,936
  - per-head q_norm and k_norm (Qwen3-specific)
  - `output.weight` is a separate tensor, not tied to the embedding
- **RTX 4070 Ti SUPER:** 66 SMs, sm_89, 16 GB, 672 GB/s nominal.
- **Correctness reference: llama.cpp.**

The README's "mode A / mode B" isn't part of the design. Remove it the next time
`README.md` is edited.

## The ceiling (estimated, not measured)

Decode at batch size 1 is limited by memory bandwidth. Per token, it reads:
- all weights except the embedding table: 1,192,230,912 bytes (file size minus
  `data_start` minus `token_embd.weight`, padding included), plus one 2 KB embedding row
- the KV cache: 28 layers × 2 (K and V) × 8 heads × 128 × 2 bytes = 114,688 bytes per
  token of context, in BF16

| Context position | Bytes per step | At 672 GB/s | tokens/s |
|---|---|---|---|
| 1 | 1.19 GB | 1.77 ms | ~560 |
| 1,024 | 1.31 GB | 1.95 ms | ~510 |
| 4,096 | 1.66 GB | 2.47 ms | ~400 |

Achieved bandwidth is usually 80–90 % of nominal, so a realistic goal is about
450–500 tokens/s at short context. Phase F replaces these estimates with measurements.

## Phases

| Phase | Builds | Proof that it's done | Depends on |
|---|---|---|---|
| A | llama.cpp reference harness | identical dumps on rerun; greedy tokens match `llama-cli` | nothing |
| B | Weights on the GPU | the device copy's checksum matches the file | milestone 8 |
| C | Reference CUDA forward pass | every layer matches A within tolerance; greedy decode matches | A, B |
| D | Compile-time plan | gtest plus `static_assert`s on the host | design first; code independent of A to C |

### A. llama.cpp reference harness

- **Builds:**
  - A script that builds llama.cpp at a pinned tag, outside the repo or in a gitignored
    directory.
  - A small program against llama.cpp's API that runs a fixed list of token IDs through
    the Qwen GGUF, one decode step at a time.
  - Through the eval callback (`cb_eval`), it dumps the named intermediate tensors per
    layer (after norm, q/k/v, after RoPE, attention output, FFN output, residual) and
    the final logits per position.
- **Proof:**
  - Two runs give identical dumps.
  - The greedy continuation equals `llama-cli`'s for the same tokens.
  - The dumped tensor names and shapes are listed in a manifest.
- **Open questions:**
  - CPU or CUDA build? CPU is deterministic and enough for a reference.
  - Where do the dumps live? Full logits are about 600 KB per position. Too much for git
    at many positions, so store them in a gitignored cache, regenerated by the script,
    and commit only the manifest and checksums.
  - Which token sequence? A short fixed prompt, tokenized once and committed as IDs.

### B. Weights on the GPU (done 2026-11-25)

- **Built:** a runtime loader in the engine: `src/weights.hpp`, `src/weights.cu`,
  `src/checksum.hpp` and `src/main.cpp`.
  1. `engine [path]` maps the GGUF with `MappedFile`. The default path is the configured
     `MODEL_GGUF`.
  2. It compares the file size with `model::file_size`, then runs the reader's `parse()`
     and compares its XXH3 hash with `model::hash`. Any other file exits 1 before the GPU
     is touched.
  3. `upload()` copies `[data_start, file_size)` into one device allocation.
  
  A tensor's device address is `base + model::tensors[i].offset`. `weights.hpp` asserts at
  compile time that every offset is a multiple of `general.alignment`, and `upload()`
  checks that the base is.
- **What C is handed:**
  - `mk::Weights`, a struct holding the device base pointer. Kernels take it by value.
  - `mk::DeviceWeights` owns the allocation through a `unique_ptr` with a `cudaFree`
    deleter. `view()` gives the `mk::Weights`.
  - `mk::HostWeights` is a `std::span` of exactly `file_size - data_start` bytes.
  - A failed CUDA call comes back as `mk::CudaError` in a `std::variant`, because nvcc
    compiles the header as C++20 and `std::expected` is C++23.
- **Proof:** a kernel computes a position-sensitive checksum of every tensor through
  offsets fixed at compile time, and of `layers[27].q` through `model::layers`. The host
  computes the same over the mapping. 311 of 311 match. With the upload shifted by 32
  bytes, 0 of 311 match (`weights_test`). `compute-sanitizer --tool memcheck` reports 0
  errors.
- **Measured** on the RTX 4070 Ti SUPER. The PCIe link runs at generation 3 x16 during the
  copy. 1,503,395,840 bytes.

  | Measure | Estimate | Measured |
  |---|---|---|
  | upload, warm page cache | 0.12–0.14 s at 11–13 GB/s, pinned | 0.167 s, 9.0 GB/s, plain `cudaMemcpy` (median of 7 runs, 0.163 to 0.201 s) |
  | upload, cold page cache | 0.4–0.75 s at 2–4 GB/s | 1.55 s, 0.97 GB/s (3 runs, 1.54 to 1.60 s) |
  | checksum kernel | 2.5–2.8 ms at 80–90% of 672 GB/s | 2.41 ms, 623 GB/s, 93% (7 runs of 5 launches, 2.40 to 2.64 ms) |

  - **Warm upload.** A pinned buffer that already holds the data copies at 13.1 GB/s, which
    is the link's rate. The file's pages are in the page cache, not in pinned memory, so
    every path that works copies them once on the host first. That host copy is the limit.
  - **Cold upload.** The file read is the limit, not the copy: a cold `dd` of the model
    alone reads at 1.0 GB/s. btrfs stores the model in 11,516 zstd-compressed extents
    under LUKS. An uncompressed copy reads cold at 1.6 GB/s and uploads in 1.0 s. The NVMe
    link runs at 8 GT/s x4. How the remaining time splits between LUKS and the drive was
    not measured, because that needs root.
  - **Checksum kernel.** A first measurement, not tuned: 4 blocks of 256 threads per SM,
    each thread reading one 8-byte word per step. 1 block per SM reads at 422 GB/s, 2 at
    583, 4 at 623 and 8 at 615, so past 4 blocks more threads do not help. That points at
    memory bandwidth as the limit, but no profiler counter confirms it yet.
- **Open questions, answered:**
  - **The copy path is a plain `cudaMemcpy` from the mapping.** Measured warm, median of 7
    interleaved runs, one process per run:

    | Path | Time | Rate |
    |---|---|---|
    | plain `cudaMemcpy` from the pageable mapping | 0.169 s | 8.9 GB/s |
    | `cudaHostRegister` with the read-only flag, then `cudaMemcpy` | fails | `operation not supported`: this GPU reports `cudaDevAttrHostRegisterReadOnlySupported` = 0 |
    | `cudaHostRegister` on a writable private mapping, then `cudaMemcpy` | 0.858 s | 1.75 GB/s; registering alone takes 0.72 s |
    | two pinned 32 MB staging buffers | 0.165 s, plus 0.039 s to allocate them | 9.1 GB/s |
    | the same with 8 MB or 128 MB buffers | 0.229 s or 0.169 s | 6.6 or 8.9 GB/s |

    The plain copy is within 3% of the fastest path that works and needs no setup. Cold,
    all paths take 1.5 to 1.6 s.
  - **`token_embd` is uploaded** with everything else. Keeping its 311 MB on the host is a
    later optimisation.
- **Limits:**
  - Only the header is hashed, so a file with the same header and other tensor data
    passes the check.
  - The checksum reads whole 8-byte words. A model with a tensor that is not a whole
    number of them fails a `static_assert` in `weights.hpp`.

### C. Reference CUDA forward pass

- **Builds:** one plain, readable kernel per op, with FP32 accumulation and BF16 weights.
  The ops:
  1. embedding row
  2. RMSNorm
  3. Q, K, V projections (matrix-vector products)
  4. q_norm and k_norm per head
  5. RoPE
  6. writing to the KV cache
  7. grouped-query attention over the cache
  8. the output projection
  9. residual add
  10. RMSNorm
  11. gate and up projections, SiLU × up, down projection
  12. residual add
  13. the final norm
  14. the LM head
  
  This is the correctness oracle for E, so clarity wins over speed.
- **Proof:**
  - Per layer and per position, compare each intermediate with A's dump: max absolute
    and relative error, plus cosine similarity.
  - Logits: the top-1 token agrees, and the KL divergence is reported.
  - Greedy decode of N tokens (N = 32 to start) matches llama.cpp. Record the first
    divergence, if any, and explain it.
- **Open questions:** the tolerances. Propose cosine similarity ≥ 0.999 per tensor and an
  exact top-1 match, then tighten them after the first measurements.

### D. Compile-time plan

- **Builds:**
  - `ModelCfg`, built from `model::meta::arch::*`
  - `GpuSpec{66}`
  - `build_layer_graph`: tiles and dependency edges for one decode step
  - `list_schedule`: a per-SM task order
  - `static_assert(acyclic(...))` and `static_assert(disjoint_writes(...))`
  
  All of it is constexpr and host-testable, with no GPU.
- **Proof:** gtest and `static_assert`s on the Qwen plan and on hand-made small graphs,
  including graphs built to fail each assert.
- **Open questions:** settle these in a design document before any code.
  - **Tile granularity:** a block of rows of each matrix-vector product, a whole
    attention head, or something else.
  - **Synchronization:** per-tile flags, per-layer counters, or grid-wide barriers. This
    decides what "acyclic" and "disjoint" have to prove.
  - **Load balance:** the matrix-vector products dominate. Their tiles should spread
    evenly over the 66 SMs.
  - **Compile-time cost:** how big a constexpr graph GCC and nvcc can evaluate before
    build times hurt. Measure it with a prototype.

### E. Megakernel

- **Builds:**
  - one block per SM, `__launch_bounds__(256, 1)`
  - each SM walks its compile-time task list from D
  - waits and signals through global memory, using the synchronization scheme D chose
  - C's ops reused as device functions
- **Proof:**
  - It matches C, bitwise where the reduction order is the same, otherwise within
    tolerance.
  - It matches A.
  - `compute-sanitizer` (memcheck, racecheck, synccheck) is clean.
  - A watchdog test shows no hang across many steps.
- **Open questions:**
  - Does one launch cover one token, or many?
  - The KV cache layout.

### F. Performance

- **Builds:** profiling (Nsight Compute and Nsight Systems) and fixes.
- **Proof:**
  - measured tokens/s at context 1, 1,024 and 4,096, against the ceiling table above
  - achieved DRAM bandwidth
  - the limiting factor named for each gap
  - a comparison with llama.cpp CUDA on the same GPU

## Parallel tracks

- **Now:** A (doesn't touch the repo's C++), and D's design document. Each runs in its
  own worktree.
- **After milestone 8 is merged:** B. It touches `src/main.cpp` and the engine part of
  CMake, the same files milestone 8 edits.
- **After A and B:** C. **After C and D:** E.

Each phase follows the same loop:
1. a short design document, approved by the user
2. an implementer session
3. an independent reviewer session
4. the verify skill, with new `features/*.md` for the phase's user-facing behaviour (use
   `/maintain-verification-skill`)
5. the user merges
